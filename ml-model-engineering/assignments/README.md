# Churn Risk Scoring — Walkthrough

This document maps every file in the repo to the rubric section it belongs
to, explains why each one is structured the way it is, and gives the exact
commands to run each piece yourself, with the output you should see.

Run everything from the repo root. Commands are shown for bash;
`python -m src.xxx` works identically on Windows/PowerShell.

See `diagrams/architecture.png` for the full system diagram and
`design_document.docx` for the write-up covering problem framing, metrics,
trade-offs, and limitations. This file is the technical map of the code.

## One-time setup

```
pip install -r requirements.txt
```

This installs pandas, scikit-learn, fastapi, uvicorn, pydantic, joblib,
pyyaml, scipy, pytest, httpx, requests, matplotlib. Nothing here needs a
GPU or downloads a large model at runtime — everything is CPU scikit-learn,
so every command below works fully offline once the dataset is loaded once
(Section A).

**Deterministic and gitignored** (regenerated by the commands below, never
committed): `data/raw/`, `data/incoming/` (except the checked-in original
source), `data/processed/`, `models/`, `artifacts/eval/`. The one thing
that *is* checked in under `data/` is `data/external/Telco-Customer-Churn-original.csv`
— the untouched source dataset — so the project is reproducible without
depending on live internet access. If you're running from a fresh clone,
run the sections in order (A → B → C → D) — each one depends on files the
previous one produced. Everything is seeded (`random_state=42`), so your
numbers should match this document almost exactly (the Random Forest can
vary in the 4th decimal place across scikit-learn/BLAS versions; the
overall pattern — which model gets promoted, and why — will match).

## Section A — Data & Features

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `data/external/Telco-Customer-Churn-original.csv` | The real, open-source **Telco Customer Churn** dataset (originally published by IBM, mirrored on Kaggle at [kaggle.com/datasets/blastchar/telco-customer-churn](https://www.kaggle.com/datasets/blastchar/telco-customer-churn)), 7,043 rows, 21 columns. | Checked in and never modified in place — every downstream script reads it and writes elsewhere, so this file is always the ground truth. `src/load_dataset.py --refresh` can re-download it from its public GitHub mirror instead of using the bundled copy. |
| `src/load_dataset.py` | `clean()` (renames columns to snake_case, fixes the 11 blank `TotalCharges` values, normalizes categorical strings like `"Month-to-month"` → `"month_to_month"`), `main()` (loads the raw CSV, cleans it, splits 90/10 into `data/raw/churn_initial.csv` and `data/incoming/churn_new_batch.csv`). | The dataset has no timestamp column, so a positional 90/10 split stands in for "historical data" vs. "a new batch that arrives later," giving `src/data_ingestion.py` (below) something real to demonstrate on. This is a documented simplifying assumption, not a hidden one. |
| `src/features.py` | `RAW_FEATURE_COLUMNS` (the 18 raw customer attributes), `engineer_features()` (adds 7 derived features), `to_model_matrix()` (both, then slices down to `MODEL_FEATURE_COLUMNS`). | This is the **one** module imported by everything else that touches a customer record — the training pipeline, the FastAPI service, and the retraining script. If feature logic lived in two places, train-time and serve-time features could silently drift apart; this file makes that impossible by construction (see `to_model_matrix()` calls in both `src/train.py` and `api/main.py`). |
| `src/data_ingestion.py` | `run_ingestion()`: seeds `data/processed/training_data.csv` from `churn_initial.csv` on first run, then validates and appends any new CSVs sitting in `data/incoming/` (de-duplicating on `customer_id`), logging what it ingested to `data/processed/ingestion_log.csv`. Moves processed files into `data/incoming/_processed/` so re-running never double-counts them. | The one-time + repeatable data-prep entry point; every script after this reads `training_data.csv`, never the raw file directly. |
| `tests/test_features.py` | Unit tests for every engineered feature (add-on counting, contract-type encoding, tenure bucketing, ordinal encodings), plus a defensive-default test for partial/missing input. | |

The 7 engineered features (`tenure_bucket`, `charges_per_tenure_month`,
`monthly_rate_deviation`, `num_addon_services`, `is_month_to_month`,
`high_value_customer`, `internet_service_encoded`/`payment_method_encoded`)
are documented feature-by-feature at the top of `src/features.py`, including
which ones are ratios vs. aggregations vs. encodings.

## Section B — Training & Offline Evaluation

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `src/train.py` | `load_and_split()` (stratified 70/15/15 train/val/test split, seeded), `build_baseline_pipeline()` / `build_candidate_pipeline()` (Logistic Regression vs. Random Forest), `evaluate_model()` (accuracy + ROC AUC), `decide_promotion()` (the guardrail: promote only if candidate val ROC AUC ≥ 0.80 **and** it isn't worse than the baseline by more than 0.01), `main()` (runs the whole pipeline and saves artifacts). | Split **once**, to disk-equivalent (in-memory from the same seeded call) rather than separately per model, so baseline and candidate are always scored on identical rows — otherwise the comparison in `decide_promotion` wouldn't mean anything. `decide_promotion()` takes a `split_label` parameter specifically so `src/retrain.py` (Section D) can reuse the exact same function to compare TEST metrics against production, not just VAL metrics between baseline and candidate — one promotion rule, two call sites. |
| `src/retrain.py` | See Section D — it imports `build_baseline_pipeline`, `build_candidate_pipeline`, `decide_promotion`, and `evaluate_model` directly from this file rather than reimplementing them. | |
| `configs/config.yaml` | Every path, split ratio, model hyperparameter, and guardrail threshold used anywhere in the repo. | One place to change `min_roc_auc` or swap the candidate's hyperparameters without touching code. |
| `tests/test_train.py` | Fits both pipelines on a sample of the real data and checks metrics are valid probabilities; `decide_promotion` tests for both the promote and reject branches using synthetic AUC values. | |

## Section C — Serving & Inference

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `api/schemas.py` | Pydantic request/response models. Every categorical field is a `Literal[...]` (e.g. `contract_type: Literal["month_to_month", "one_year", "two_year"]`), so a malformed request is rejected with a 422 before it ever reaches the model. | |
| `api/main.py` | FastAPI app. `GET /health` (returns `model_not_loaded` instead of crashing if training hasn't run yet), `POST /predict` (calls `src.features.to_model_matrix()` — the **same** function `src/train.py` uses — then the loaded model's `predict_proba`). Model is loaded once via a `lifespan` startup handler, not per-request. | Serves `models/production_model.pkl`, whichever model `train.py`/`retrain.py` most recently promoted — the API never hardcodes "Random Forest" anywhere, it just reads `model_version.json`. |
| `scripts/load_test.py` | Sends N sequential requests to a running `/predict` and reports avg/p50/p95/max latency. | Separate from the test suite on purpose — it needs a live server and is meant to be run manually against whatever's currently deployed, not as part of CI. |
| `tests/test_api.py` | FastAPI `TestClient` tests: health check, a full predict round-trip, and a validation-rejection case (bad `contract_type` → 422). Uses `with TestClient(app) as client:` specifically — FastAPI's `lifespan` startup hook (which loads the model) only fires inside that context manager; a bare `TestClient(app)` silently skips it and every predict call 503s. That cost real debugging time during development and is worth calling out. | |

## Section D — Monitoring, Data Quality & Retraining

### Files

| File | What it does | Why it's structured this way |
|---|---|---|
| `src/monitoring.py` | `check_data_quality()` (missing-value fraction + negative-value checks), `check_drift()` (per-feature mean vs. training mean, expressed as a z-score; std==0 handled explicitly rather than dividing by zero), `run_monitoring_report()` (runs both against the last 400 rows of the processed table as a stand-in for "the most recent batch"). | Uses raw numeric columns already in the processed table (`tenure_months`, `monthly_charges`, `total_charges`, `senior_citizen`) as the drift signal — cheap to compute and doesn't need ground-truth labels, unlike a real performance metric (which needs someone to confirm actual churn outcomes first). |
| `src/retrain_trigger.py` | `RetrainSignals` / `RetrainDecision` dataclasses, `should_retrain()`: fires if **any** of (a) ≥7 days of new data, (b) recent labeled-feedback AUC has dropped ≥0.03 vs. production, (c) drift z-score ≥2.0. | This only decides **whether** to retrain — it deliberately does not retrain anything itself, so it can be called cheaply and often (e.g. from a daily cron job) without the cost of actually retraining every time it's checked. |
| `src/retrain.py` | `load_current_production()` (reads what's deployed now), `run_retraining()`: retrains baseline + candidate on the **current** `data/processed/training_data.csv` (which ingestion has already been growing), picks the better of the two using `decide_promotion()` exactly as `train.py` does, then compares *that* result's test ROC AUC against the currently-deployed model's test ROC AUC using the **same** `decide_promotion()` function again. Promotes and archives the old model under `models/archive/<old_version>/`, or — if not promoted — saves the attempt under `artifacts/eval/retrain_candidates/` and leaves production untouched. | This is what a scheduler would call once `should_retrain()` says yes — the two files are separate specifically so "check if we should retrain" (cheap, frequent) and "actually retrain" (expensive, rarer) are independently testable and independently callable. The training pool isn't reassembled here from separate "new labels" files — `src/data_ingestion.py` already appends every new batch into `training_data.csv` as it arrives, so "retrain on the current data" and "retrain on everything ingested so far" are the same operation by construction. |
| `tests/test_monitoring.py` | Drift-detection tests on synthetic distributions (no drift, a clearly shifted feature, a zero-variance edge case), data-quality tests (missing values, negative values), and a JSON-serializability regression test for the full report (numpy `bool_`/`float64` values silently breaking `json.dumps` is a common real bug in this kind of code — `check_drift()`'s explicit `float()`/`bool()` casts exist because of exactly that). | |
| `tests/test_retrain_trigger.py` | Each of the three signals tested independently (fires / doesn't fire at the threshold), plus a combined case where all three fire at once. | |
| `tests/test_retrain.py` | `run_retraining()` tested against a `tmp_path`-scoped config (never touches real `models/`/`artifacts/`) for three scenarios: no current production yet (must promote), a forged much-stronger current production (must reject and save to `retrain_candidates/`), and a forged weak current production (must promote **and** archive the old model file). | |

## Incident scenario: upstream schema change

(Also written up in `design_document.docx`, Section 5.3.) Suppose an
upstream billing-system migration silently renames the `Contract` field, or
starts sending an unexpected new value (e.g. `"Month to month"` without the
hyphen). A missing/renamed column is caught immediately: `src/data_ingestion.py`
validates every incoming file's schema against `src/features.py::RAW_FEATURE_COLUMNS`
and refuses to ingest it — loud failure, logged, no bad data enters
`training_data.csv`. A changed *value* within an existing column is subtler:
it passes ingestion but gets encoded as an unrecognized category by
`src/features.py`'s mapping logic, silently degrading `is_month_to_month`
for affected rows. That's exactly the kind of shift `src/monitoring.py`'s
drift check is designed to catch. On-call response: (1) check
`data/processed/ingestion_log.csv` for which batch introduced it, (2) patch
the category mapping in `features.py`, (3) re-ingest the affected batch,
(4) run `src.retrain`. If it's already affected production predictions,
the immediate mitigation is to restore `models/archive/<previous_version>/`
over `models/production_model.pkl` while the fix is developed.
